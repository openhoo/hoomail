# Hoomail Inspect review — November 25, 2026

Compared release 0.10.3 (`b65bc85`) with the revised offline inspector. The release passed its existing Go inspector tests but failed 17 of 54 assertions on five ordinary SMTP messages. The revised binary passed all 54. Several assertions check different consequences of the same bug.

## What changed

| Area | What the comparison found |
| --- | --- |
| Message headers | A responsible sender different from the author received an “unnecessary Sender” warning. An internationalized line could exceed 78 bytes without exceeding 78 characters. The inspector now distinguishes the author from the sender, applies the character recommendation separately from the byte limit, and checks dates, IDs, address groups and field syntax. |
| MIME and attachments | A message containing only two attachments reported each twice. A selected body with an unknown charset could be reported as empty. The inspector now reports unknown decoded sizes, recognizes valid bodyless messages, and distinguishes empty multiparts from decoded leaves. The built-in plain sample also had an actual MIME defect: its attachment's base64 line exceeded 76 characters. All four built-in sample types now pass the format checks. |
| Authentication and lists | A valid `Authentication-Results: mx.example; none` was rejected. The inspector now recognizes it and distinguishes malformed DKIM or ARC structure from an unverified claim. One-click reports check the required header pair and identify the actual DKIM header occurrence claiming coverage of both fields. |
| HTML accessibility and privacy | A bookmark counted as an unnamed link, and a half-opacity logo counted as a tracker. On a fixture of hidden and visible links, Chromium exposed eight links, two unnamed; Hoomail now matches those counts and the other six names. Resource order follows the markup. Responsive image candidates are listed without fetching them or guessing which image a client would display. |
| HTML/CSS compatibility | Whitespace in `display: grid`, SVG query strings and real CSS in stylesheets could change or erase a result. Conversely, comments and strings could trigger detections. The inspector now reads CSS tokens and separates HTML attributes from CSS properties. Unknown client verdicts and annotated yes/no verdicts no longer turn into partial support. |
| Partial reports and UI | The API could emit `evidence: null` for its truncation marker and the browser could crash on opening the report. A real SMTP case now exercises the complete rendering path. Clipped legacy HTML no longer yields a clean privacy verdict for the unseen suffix. Warning and advisory icons now agree with the summary buckets. |

## Independent comparisons

- **SMTP → HTTP:** The [repeatable smoke](../../scripts/smoke-inspect.py) sends delegated mail, a newsletter, an invalid one-click claim, an attachment-only message, and an unknown-charset message. It compares raw bytes, unread state, findings, resource counts and client verdicts. Python's standard email parser and SHA-256 provide the attachment check. The smoke starts its own process and temporary database; CI runs it against the binary built for Playwright.
- **Mail standards:** Positive and negative fixtures cover [message format](https://www.rfc-editor.org/rfc/rfc5322), [internationalized headers](https://www.rfc-editor.org/rfc/rfc6532), [MIME](https://www.rfc-editor.org/rfc/rfc2045), [Authentication-Results](https://www.rfc-editor.org/rfc/rfc8601), [DKIM](https://www.rfc-editor.org/rfc/rfc6376), [ARC](https://www.rfc-editor.org/rfc/rfc8617) and [one-click unsubscribe](https://www.rfc-editor.org/rfc/rfc8058). Tests distinguish an absent or malformed claim from a syntactically usable but unverified one.
- **Can I Email:** Updated the exact bundled export from July 20 to September 16, 2026. Compared every one of its **15,808** client/platform/version verdicts and available numbered notes. The snapshot has **935 unknowns**. Unknown entries remain visible but do not contribute to support percentages.
- **Feature detection:** Hoomail covers **242 of the 308** published feature matrices and adds [Mailpit's script rule](https://mailpit.axllent.org/docs/usage/html-check/). Against the independent [Can I Email fixture source](https://github.com/hteumeuleu/caniemail/tree/cb8109c3f8658e003aa064b47a71b232ddc28d39), it detected the target feature in **240 examples across 126 HTML files**. Local fixtures cover command attributes and explicit APNG sources: the former has no upstream example and the latter's upstream image uses an ordinary PNG URL. The script rule reproduces Mailpit's published two-element, 50% example. Negative controls cover CSS-like strings, unrelated attributes, and filenames in query strings.
- **Browser and Go:** **47/47 Chromium tests passed**, including a real SMTP newsletter, truncated results, retry after failure, and isolation from external content. The full Go race suite passed, as did TypeScript, the client build, Go vet and module verification. The local workflow linter reported the same pre-existing `code-quality` permission diagnostic before and after the CI change.

[Reproduction commands](../development.md#inspect-comparisons) include the optional upstream corpus. These pre-release checks used local, disposable mailboxes.

## What the results mean

A successful format check describes the stored bytes. It does not verify DNS, signatures, endpoint behavior or delivery. A tracking pixel is a candidate, not proof of tracking. Accessible names and visibility come from static markup; external stylesheets and complete client layout are outside the checker. The overall compatibility score is a heuristic, not an audience success rate. Unconfigured features, including some selectors and units, receive no verdict.
